Java Memory Playground

Draw what a Java program has in memory: the call stack on one side, the objects on the heap on the other, and the references between them. Nothing here runs your code — you build the picture, which is what makes it a thinking tool rather than a debugger.

Reading a diagram

A diagram has two kinds of box. A stack frame is one method call, labelled with its depth and name, holding that call's local variables. An object is one instance on the heap, labelled :ClassName and holding its fields.

An arrow is a reference. It leaves the exact variable or field that holds it, so you can see which field of which object points where. A variable with no arrow holds null.

Frames stack in call order, and only the frame on top can return — the return button on the others is disabled, because a call in the middle of the stack cannot finish before the ones above it. That restriction is the lesson, so the button stays visible rather than disappearing.

Building one

The palette in the top left corner is the source of new things. Drag one onto the canvas:

  • new ClassName — an instance of one of your configured classes, with a field for each attribute.
  • new Array — pick a length and an element type.
  • Call Method — a new frame on top of the stack.
  • Declare Global Variable — a variable belonging to no frame. Java has no globals; this is scaffolding for the lessons that come before methods do.

To make a reference, drag from the handle on the right of a variable or field to the object it should point at. Drag the arrow away again to set it back to null. Inside a frame, Declare Local Variable adds a variable, and return pops the frame — along with the references it held, which is often what makes something garbage.

Values and references

Primitive fields are edited in place: a number field for the numeric types, a checkbox for boolean. Reference fields get a handle to drag an arrow from instead.

A String is shown inside the thing that references it, in quotes, rather than as its own box on the heap. A diagram about a linked list should not sprout a box for every name. When the point of the lesson is that a String is an object like any other — == against .equals(), the string pool — turn inlineStrings off and it gets a box and an arrow like everything else. The object is there either way; only the drawing changes.

Steps and traces

A diagram can be a single picture or a sequence of them. The bar along the bottom moves between steps, and each step can carry a label saying what happens there — head = new Node(1).

Add step duplicates the current step and continues from it, so a trace is built by changing one thing at a time. What changed since the previous step is marked, which is usually the whole point of a trace; hideStepChanges turns that off.

A step can be marked as an exercise. The student is handed the previous step and builds this one themselves, then checks their answer against what the step actually contains.

The garbage collector

Run Garbage Collector removes every object that cannot be reached from a variable or a stack frame. Unreachable objects are already tinted before you press it, so you can see what is about to go.

With the gcPrediction option on, you commit first: click the objects you believe are unreachable, then Check and collect scores what you found, what you missed, and what you marked that was still reachable. Committing to an answer before seeing it is where the learning is.

The teacher's playground — the ?edit URL

There are two playgrounds, and which one you get is decided by the URL.

URL What you get
the app’s address The student's playground: the whole diagram, every edit, and the steps of a trace to walk through.
the same, with ?edit The teacher's: the same, plus class configuration and step authoring.

/edit as a path works too, where the host has a rewrite rule for it. The query flag ?edit always works, because the app is served as static files.

The split is about which tools are on screen, not about what a student is allowed to touch. A student still builds objects, connects references, walks the steps and runs the collector. What the teacher's playground adds is deciding which classes exist and what the steps are — the setup for an exercise, not the working of it.

The diagram itself lives in the part of the URL after the #, and the mode is deliberately kept out of it. That means one diagram has both an editing link and a working link: take a link you saved from the teacher's playground, drop the ?edit, and you have the student's view of the same picture.

Classes from Java source

The teacher's playground asks for your classes instead of making you describe each field through a dialog. Paste the Java: 

class Node {
    int value;
    Node next;
}

Only the structure is read — the class names, and the name and type of each field. Method bodies are skipped and nothing is executed. Records work too, and their components are read as fields.

Applying classes reaches every step of the diagram, so when a change would cost something already drawn, you are told what before it happens: which field is about to be deleted from how many objects, and which objects belong to a class that no longer exists. A field that holds nothing — an untouched int still at 0, a reference still null — is not counted, because losing it costs nothing.

Options

Options are part of the diagram, so they travel with a shared link. The configuration view has presets — References only, With the stack, Everything — for the common shapes of lesson. The individual switches:

Option Default Effect
hideSidebar off Hide the palette, for a diagram meant only to be read.
hideCallMethod off Drop Call Method from the palette.
hideDeclareGlobalVariable on Drop Declare Global Variable. On by default, because Java has no globals.
hideNewArray off Drop new Array.
disableGarbageCollector off No collector button, and no tinting of unreachable objects.
gcPrediction off Ask which objects are unreachable before collecting them.
createNewOnEdgeDrop off Dropping an arrow on empty canvas creates the object it points at.
inlineStrings on Draw a String inside its holder instead of as its own heap box.
hideSteps off Hide the step bar, for a lesson about one picture.
hideStepChanges off Stop marking what a step changed since the one before it.

A shortcut is never taken from someone typing into a field. In an embedded playground the bindings can be changed, or unbound, through the keyBindings attribute.

Sharing a diagram

Save (URL) writes the whole diagram — classes, options, every step — into the address bar, compressed and encoded after the #. The link is the document: send it to a class, put it in a worksheet, or bookmark it. There is no account and nothing is stored on a server.

Because the state is in the fragment, it never reaches the server, and a very large diagram makes a very long link. Download (PNG) exports the picture, and with more than one step, Download all steps gives one image containing the whole trace for a printed worksheet.

B&W switches the whole playground to black and white, and the downloads follow. It is not a filter over the colours: the heap turns white, a stack frame grey, and everything the diagram was saying in colour is said again in line style: an unreachable object is the box with a dotted border, and what a step changed is dashed — the ring around a node, or the reference itself. Photocopy it and it still reads.

Embedding

The playground is published as a framework-agnostic web component. Two elements are defined, matching the two playgrounds: 

<script src="path/to/index.umd.js"></script>

<!-- the student's -->
<java-memory-playground id="playground"></java-memory-playground>

<!-- the teacher's -->
<java-memory-playground-editor></java-memory-playground-editor>

<script>
  const playground = document.getElementById("playground");
  playground.setAttribute("memory", JSON.stringify(diagram));
  playground.addEventListener("change", (e) => console.log(e.detail));
</script>

The bundle is published as @java-memory-playground/web-component. An embedded playground never touches the URL of its host page, and several of them can share one page. Both elements take the same attributes:

Attribute Type Meaning
memory string The diagram, as JSON or as a saved link's fragment.
options JSON The options above, overriding what the diagram carries.
language string en or de. Follows the browser otherwise.
step number Which step to show, counted from zero, so prose around the diagram can walk a reader through a trace.
persistence boolean Off for an embedded playground: it must not take over the URL of the page hosting it.
keyBindings JSON Overrides for the shortcuts above.

It reports back with two events: change, carrying the whole diagram when the user saves, and stepchange, carrying the step index whenever the shown step moves.

For a React application, the component is also published on its own as @java-memory-playground/java-memory-playground.

.jmp files and VS Code

A .jmp file is exactly the JSON that a shared link carries, so a diagram moves between the app, an embedded playground and a file unchanged. It is an ordinary text file: diffable, reviewable, and fine to keep in a repository next to the code it illustrates.

Java Memory Playground Studio opens those files in VS Code as diagrams rather than as JSON, with the editor's own undo and save. Show Source switches to the JSON and Show Diagram switches back.
